# AGENTS.md

Guidance to coding agents working in this repository.

## Project

diffsplainer is a GitHub PR review app. It shows a PR's diff as chunks, with an explanation from a headless Claude Code run next to each chunk. At runtime the backend uses only the Python 3.11+ standard library. The browser UI is plain HTML, CSS and JavaScript in `src/diffsplainer/static/`. pytest and ruff are the dev dependencies, in the `dev` group. Do not add runtime dependencies.

## Commands

- Run the app: `uv run diffsplainer`, or `uv run diffsplainer <PR URL>` to also open that PR in the browser. `uv run diffsplainer --local [path]` reviews a repository's unpushed commits instead (see "Local review"). The README lists the environment variables.
- Run the tests: `uv run pytest`.
- Check syntax: `uv run python -m compileall -q src`.
- Lint and format: `uv run ruff check` and `uv run ruff format`.

## Tests

Write or change the test first and see it fail before you change the code. Tests live in `tests/` and replace GitHub (`diffsplainer.github` functions) and Claude (`explain_file`, `explain_overview`, `explain_term`) with fakes. Tests of local review run against a temporary git repository with a bare upstream (the `repo` fixture in `tests/conftest.py`); they replace Claude, and GitHub where a test covers related PRs. Tests of `run_claude` point `CLAUDE_BIN` at `tests/fake_claude.py`, which records its arguments, working directory and environment and answers each schema the app sends (term, chunk batch, overview) with fake text. They never call the network or the real `claude` CLI. Browser checks can run the app with `CLAUDE_BIN=$PWD/tests/fake_claude.py` to avoid real Claude calls.

## Dependency updates

Dependabot opens weekly grouped updates for GitHub Actions and uv. Patch and minor updates auto-merge once the required CI checks pass; major updates wait for a human.

## Layout

- `diff.py` parses GitHub patches into chunks and marks generated files.
- `github.py` is the GitHub REST client.
- `context.py` gathers project instructions and related PRs, or, for local review, reads the instruction files and the branch's plan from disk and finds related PRs for an `origin` on GitHub.
- `local.py` finds the unpushed commits of a repository and chunks their combined diff.
- `review.py` reads and writes the review file.
- `claude.py` builds prompts and runs `claude -p`.
- `server.py` serves the API, the static files and the caches.
- `static/vendor/` holds the vendored Prism (`prism.js`) and its licence (`prism-LICENSE.txt`).

## Releasing

1. Bump `version` in `pyproject.toml`.
2. Merge the change to `main`.
3. Tag `vX.Y.Z` on `main` and push the tag.
4. The release workflow publishes to PyPI through trusted publishing (environment `pypi`) and creates the GitHub release.
5. Write the release notes afterwards with `gh release edit <tag> --notes-file <file>`.

## How it works

1. **Diff.** `get_pull_files` requests pages of 100 files until GitHub returns a short page, up to 30 pages, which is GitHub's limit of 3000 files per PR. Each hunk becomes a chunk. A hunk of more than 30 lines is split at runs of unchanged lines, or, for long runs of additions or deletions, at top-level blocks. Files are listed in the order of the Files changed tab (`tree_order`): directories before files, compared case-insensitively.
2. **Context.** Instruction files come from the base commit: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md` and `CONTRIBUTING.md` at the root, plus nested `CLAUDE.md` and `AGENTS.md` in directories that contain changed files. `README.md` is a fallback, used only when none of those files was loaded. Related PRs come from the last three commits of each of the first eight changed files. At most 12 commit SHAs are mapped to merged PRs, taken round-robin across the files (first commit of each file, then the second, and so on) so that one busy file cannot use up the cap.
3. **Size cap.** A PR whose additions plus deletions, not counting generated files (item 9), exceed `MAX_CHANGED_LINES` (default 1000) gets one `error` event with `scope: "limit"` and no Claude calls. The diff still loads through `/api/pr`. One batch targets 400 diff lines, but a single chunk longer than that becomes its own batch, so a batch can exceed the estimate. Measured on this repository's PR#1 with the `sonnet` default and a Claude Code login: a batch of 6 chunks (298 diff lines) used 10.6k input tokens and 1.5k output tokens, took 11 s of Claude time and cost $0.057. A batch of 7 chunks (143 diff lines) used 8.6k input tokens and 1.8k output tokens, took 13 s and cost $0.047. Before the isolation flags, an 11-chunk batch in the default Claude Code setup (Opus, with the user's MCP connectors, hooks and `CLAUDE.md` loaded) used 215k input tokens and 3.8k output tokens, took 39 s and cost $1.80, so a PR of 14 calls cost about $25. The overview call is not measured. 1,000 changed lines are about 1,500 diff lines with context, which is 5–8 batches. Extrapolated from the two measured batches, not measured: about $0.25–0.45 and 45–85k input tokens per PR, plus the overview, taking about 15–30 s in total at `CLAUDE_CONCURRENCY=6`.
4. **Explain.** `claude -p` runs with tools disabled and a JSON schema, once per file batch plus once for the overview, in parallel (`CLAUDE_CONCURRENCY`, default 6). Each call passes `--strict-mcp-config`, `--setting-sources ""`, `--disable-slash-commands` and `--no-session-persistence` and sets `ENABLE_CLAUDEAI_MCP_SERVERS=false`, because Claude Code loads the user's MCP servers, hooks and `CLAUDE.md` whatever its working directory. User settings do not load, so `CLAUDE_MODEL` defaults to `sonnet`, and authentication that comes from settings (such as `apiKeyHelper`) does not apply; the Claude Code login does. Every call runs in one private directory per process (`tempfile.mkdtemp`, mode 0700, created on first use and removed at exit), because Claude Code loads `CLAUDE.md` and `.claude/settings.json` from its working directory and `/tmp` is world-writable. One directory for all calls also keeps the working directory in Claude Code's prompt the same between calls. Each explain request also starts a watcher thread that checks the client socket every 0.5 s with `select` and `recv(1, MSG_PEEK)`, which does not consume request bytes. When the client has closed the socket, the watcher sets `gone`. `run_claude` then kills its `claude` process and raises `ClaudeCancelled`, queued batches do not start, no `error` events are sent, and the log is not cached. The PR title, description, project docs, related PRs and file list go inside `<pr_context>`, and diffs go inside `<chunk>` and `<diff_excerpt>`. The system prompt tells Claude that text inside those tags is data from the PR author, not instructions. The tags are not escaped, so content that contains a closing tag can end its block early. The chunk and overview schemas' field descriptions are the prompt for each field: `what` is the effect in one sentence, `why` is the stated reason or "Reason not stated in the PR", and `concern` is a specific, verifiable risk or empty. In the overview, `summary` is the outcome and its stated reason in two sentences at most, `approach` is the main design choice, and `review_focus` lists up to three specific risks. `SYSTEM` sets the writing style (plain language) for every Claude call, chunk batches and overview alike. A selected term is explained by a separate call, `explain_term`: its prompt is `SYSTEM`, the PR title and description (no project instructions or related PRs, so a click takes a few seconds), the chunk when there is one, and the paragraph and the selection in `<paragraph>` and `<selection>` tags. `TERM_SCHEMA` has `meaning` (what the term means in general, one or two sentences) and `here` (what it does in this PR, one sentence).
5. **Stream and caches.** Results stream to the page as Server-Sent Events (`status`, `context`, `overview`, `chunk`, `error`, `done`). When the stream ends, a chunk that has no explanation shows "No explanation returned". A finished stream is kept in `_explain_cache` (LRU, 50 entries) under `owner/repo/number@baseSha..headSha:prs`. A stream is cached only if every call succeeded and every batch got explanations for all of its chunk ids, so an incomplete result is asked for again on the next open. `_pr_cache` holds loaded PRs for 60 seconds (LRU, 50 entries) and drops an expired entry when it sees it. `GET /api/explain-term/<owner>/<repo>/<num>?text=<selection>&around=<paragraph>&chunk=<id>` returns `{"meaning", "here"}` as JSON (`chunk` is absent for the overview). It answers 400 for empty `text`, `text` over 300 characters or `around` over 4,000 characters, 404 for a chunk id that is not in the PR, and 502 with `{"error"}` when Claude fails. It starts the same disconnect watcher, so aborting the request kills the Claude call and nothing is written. `_term_cache` (LRU, 200 entries) holds the answers under a tuple of owner, repo, number, base SHA, head SHA, chunk, selection and paragraph; a failed call is not cached.
6. **Token.** `_token()` in `github.py` resolves the GitHub token once per process: `GITHUB_TOKEN`, then `GH_TOKEN`, then `gh auth token`, else none.
7. **Network.** The server binds to `127.0.0.1`. It has no authentication, and it uses the user's GitHub token and Claude Code login, so it must not be reachable from other machines. Binding alone does not stop web pages in the user's browser, so the server also refuses any Host name other than `localhost`, `127.0.0.1` or `[::1]` (DNS rebinding; any port, so SSH tunnels work), and refuses `/api/` requests that the browser marks as coming from another site (`Sec-Fetch-Site`). The second check depends on the browser sending that header, which all current browsers do. Keep both checks.
8. **Syntax highlighting.** `static/vendor/prism.js` is Prism 1.30.0 as one minified file (88 KB): the core plus 35 grammars: markup, css, clike, javascript, c, cpp, go, python, php, java, yaml, markdown, sql, graphql, typescript, jsx, gdscript, tsx, scss, json, bash, rust, ruby, toml, csharp, kotlin, swift, dart, lua, docker, makefile, ini, hcl, powershell and less, plus `markup-templating`, which `php` needs. They are concatenated in dependency order. The version and the grammar list are in its first-line comment. The second line, `window.Prism = window.Prism || {}; Prism.manual = true;`, comes before the core so that Prism does not highlight the page by itself. There is no autoloader and there are no plugins. The app serves the file, so the page loads no script or style from another host. To rebuild it or add a grammar, run `npm pack prismjs@<version>`, unpack the tarball, and concatenate the comment line, the `Prism.manual` line, `components/prism-core.min.js` and `components/prism-<id>.min.js` for each grammar in the order that this command prints (it reads `require` and `modify` in `components.json`, for example `markup` before `css`, `clike` before `javascript` and `markup-templating` before `php`): `node -e "const d=process.argv[1];console.log(require(d+'/dependencies.js')(require(d+'/components.json'),process.argv.slice(2)).getIds().join(' '))" <unpacked package dir> <ids...>`. Then update the comment, copy `LICENSE` to `prism-LICENSE.txt` and add the extension to `LANGS` in `app.js`. `langOf` first matches the base file name against `NAME_LANGS` (`Dockerfile` and `Dockerfile.*` give docker, `Makefile`, `GNUmakefile` and `*.mk` give makefile, `.env.*` gives ini), then picks the grammar from the file extension, and `renderChunk` writes it to `data-lang` on the chunk's `.diff`; files with neither stay plain. One `IntersectionObserver` (`rootMargin` 200px) calls `highlight` once for each `.diff` as it nears the viewport, so a long PR costs nothing up front. `highlight` replaces each `td.s` with `Prism.highlight(td.textContent, ...)`, which escapes its input, so raw diff text never goes into `innerHTML`. Lines over 1,000 characters (minified code) stay plain, and so do chunks of more than 1,500 rows (a lockfile or generated file in one hunk), because highlighting them in one observer callback would block the page. If `Prism` is undefined (its script failed to load), the observer is not created and all code stays plain. `setApp` replaces the page content and disconnects the observer first, so detached diff tables are not kept in memory. Each line is highlighted alone, so the middle lines of a multi-line comment or string are coloured as code. Measured on django/django PR#17910 (54 chunks, 1,146 lines): highlighting every chunk takes about 17 ms. The token colours are `--tok-*` in `style.css`, for both themes. Each has at least 4.5:1 contrast on `--panel`, `--add-bg` and `--del-bg`; check again when you change a colour or a background. The `.tag` rule applies only inside `.file-head`, because Prism also gives tag tokens the class `tag`.
9. **Generated files.** `chunk_files` sets `generated` on each file. It is true when the base name is in `diff.GENERATED_NAMES` (`package-lock.json`, `npm-shrinkwrap.json`, `composer.lock`, `yarn.lock`, `pnpm-lock.yaml`, `uv.lock`, `poetry.lock`, `Pipfile.lock`, `Cargo.lock`, `Gemfile.lock`, `go.sum`) or the path is in the set the caller passes. Local review passes `local.generated_paths`: one `git check-attr -z --stdin linguist-generated` run in the work tree for all changed paths, where the value `set` or `true` counts and a git failure gives no paths. `local.changes` runs it, so it is cached with the chunks and a `.gitattributes` edit shows only when HEAD changes or the app restarts. PR mode has no checkout and passes nothing, so only the base names count. It does not fetch `.gitattributes`, because `project_instructions` reads files at the base commit, not the head. A generated file does not count toward `MAX_CHANGED_LINES` (`_explain` subtracts its additions and deletions from the PR totals, `_explain_local` leaves it out of the sum), `explain_changes` makes no `explain_file` call for it and leaves it out of the overview's files, and the prompt's file list still names it. The page renders it as a collapsed `<details>` whose `<summary>` is the file head with the note "Generated file, not explained.". Its chunks have no explanation column and no skeleton, so nothing waits for an explanation; in local mode they keep Request changes and Comment.

`GET /api/version` returns `{"version", "commit"}`: the installed package version (`null` if not installed) and the short SHA of the Diffsplainer checkout (`null` outside one). `app.js` fills the footer (outside `#app`) from it.

## Local review

`diffsplainer --local [path]` reviews the unpushed commits of one repository. `main()` stores the resolved path in `server.LOCAL_REPO` and exits at start-up if `local.current_range` fails (not a repository, no upstream and no default branch, or an unreadable review file). The browser never sends a path, so no request can name another repository. Without `--local`, `LOCAL_REPO` is `None` and `/api/local`, `/api/local/explain`, `/api/local/explain-term` and `/api/review` answer 404.

1. **Range.** `local.current_range` takes the merge-base of HEAD with `@{upstream}`, else with `refs/remotes/origin/HEAD`, `refs/heads/main` or `refs/heads/master`, else raises `ValueError` ("default branch"). The merge-base, not the upstream tip, keeps the commits of a diverged upstream out of the range. `local.ranges` returns it with the base and HEAD; `load` also reports it as `local.merge_base`, because it is the commit GitHub has, which the base is not once a review round has recorded an unpushed head. If the newest `reviews[].head` in the review file is a full SHA, is in the range and is an ancestor of HEAD, it becomes the base (the next round). The file is written by another program, so every other value is ignored and nothing from it goes to git unchecked.
2. **Read-only.** `local.py` runs `rev-parse`, `merge-base`, `log`, `diff`, `blame`, `check-attr`, `branch --show-current` and `remote get-url origin`, and never `add`, `apply`, `commit` or `update-ref`. `git log` gets `--no-show-signature` because a user's `log.showSignature` would print into the format. `git diff base head` is split per file and the names come from `--name-status -z`, so quoted paths are not parsed. A type change (a file that becomes a symlink, for one) is one name but two patches, a deletion and a creation, which become one file. The files go through `chunk_files` like a PR's.
3. **Chunk to commit.** `load` gives each chunk a `sha`. A chunk with added lines gets the newest commit that wrote one of them (`git blame --porcelain` of the file over the range; only added lines are blamed). A deletion-only chunk gets the newest commit that deleted one of its lines: `git blame --reverse` over the range names the last commit in which the line existed, and the next commit in the range deleted it. `sha` is `None` when git cannot blame the file. `local.changes` caches the commits and tagged chunks of the last 8 ranges (repository, base, HEAD), because `/api/local`, the explain stream and each term click all load them. Merge commits, binary files and uncommitted changes are out of scope.
4. **Routes.** `GET /api/local` returns `{local: {repo, branch, base, head, merge_base, commits, summary}, files, review}`. `GET /api/local/explain?base=&head=` streams the same events as `/api/explain` through `Handler.stream` and `explain_changes`, which `/api/explain` shares. `base` and `head` are the `local.base` and `local.head` the page rendered. Chunk ids (`f{i}c{j}`) number the chunks of one diff, so the route explains exactly that range, `local.load(repo, base, head)` with `local.merge_base` taken from `head` (`local.upstream_merge_base`), and not the range HEAD gives by now. `local.pinned_range` checks them first: both are full SHAs, `base` is an ancestor of `head` (or equal) and `head` is an ancestor of the current HEAD (or equal), so a `head` older than HEAD is fine and the agent's later commits do not move what the page's explanations refer to. Anything else, or a missing parameter, streams one `error` event with scope `fatal` that tells the page to reload, and no Claude run starts. Its cache key is the repository path, base, HEAD, the related-PR limit and a short hash of the summary and plan (see item 8); an empty range streams only `done`, and `MAX_CHANGED_LINES` applies. `?prs=N` sets the limit like it does for a PR (`parse_pr_limit`: default 3, clamped to 0 to `MAX_PRS`). `context.local_related_pulls` runs beside `local_instructions` and calls `related_pulls` with the owner and repository from `local.origin_repo` (the `origin` URL as `https://`, `git@` or `ssh://` for the host of `GITHUB_API`, `github.com` by default), no PR number and `local.merge_base` as the base, so it only looks at history GitHub has. With no GitHub origin, or when GitHub fails (no token, offline, a 404 for a private repository), it returns no PRs and the review goes on. The local review only reads from GitHub. The prompt context is `claude.context_block` with a `local` entry (branch, commit subjects and bodies, files) in place of `pr`; each `<chunk>` carries its `commit`; `context.local_instructions` reads the instruction files from the work tree and skips a file whose real path is outside the repository. `GET /api/local/explain-term?text=&around=&chunk=&base=&head=` answers `{meaning, here}` like `/api/explain-term`, through the shared `Handler.answer_term` with the `local` context, built from the range `base` and `head` name, checked by `local.pinned_range` as for the stream before anything else (a bad or missing pair is a 400 with the same reload message); its cache key is the repository path, base, head, a short hash of the summary (`prompt_digest`), chunk, text and paragraph.
5. **Write endpoint.** `POST /api/review` takes JSON `{action, ...}` with `action` `change`, `question`, `status` or `start`; `review.apply` validates it, and the server answers 400 for a bad request, 409 for an unusable review file and 500 when git fails to give the range. Besides the Host check, it needs `Sec-Fetch-Site: same-origin` (a missing header is refused, unlike on GET), `Content-Type: application/json`, and a `Content-Length` of at most `MAX_REVIEW_BYTES` (256 KiB), and it closes the connection because refused requests leave their body unread. A `sha` or `head` in a request must be a commit of the current range, except that the current HEAD (which `Handler.do_POST` passes to `review.apply`) also names a `start` and a general comment (a `change` with an empty `file`). An agent that answers with replies only and no commit leaves the range empty, and the round still has to end. A chunk entry or question still needs a commit of the range. `start` ends a round: it appends `{head, at}` to `reviews`, and with `approve: true` (a boolean; anything else is a 400) it also adds the commits of the current range up to and including `head` to `approved`, without duplicates, so a commit the agent made after the page loaded stays unapproved (`Handler.do_POST` passes the range to `review.apply` as a list, oldest first); on an empty range it approves nothing and still records the round. Both happen in one `review.update`, so the agent never sees a round without its approvals. With `approve` (`start_review` gets a list, empty for an empty range; a plain `start` passes `None`), `start_review` raises `ValueError` (a 400) while any entry is open, meaning any dict entry whose `status` is not `resolved`, as on the page. There is no action that approves one commit. A GET on `/api/review` answers 405.
6. **Review file.** `review.path` is `git rev-parse --absolute-git-dir` plus `diffsplainer/review.json`, which also works in a linked worktree. The format is in `skill/diffsplainer-review/SKILL.md`. Every write (`review.update`) takes a lock, reads the file, edits the data, writes `review.json.<pid>.tmp` and `os.replace`s it, so it keeps a reply the agent wrote after the page loaded, and every field it does not know. The lock covers only this process, and the agent writes from another one, so before the replace `update` checks that the file is byte for byte what it read (or still missing). If it changed, `update` reads again and runs the edit again, up to 5 times, then raises `ReviewError` ("keeps changing"), which is a 409. An edit therefore must be safe to run more than once on fresh data. An agent can still overwrite Diffsplainer's write if it writes in the short window between that check and the replace. A file that is not valid JSON, or whose `reviews`, `approved` or `entries` is not a list, is never overwritten: the write raises `ReviewError`. Diffsplainer never writes `reply` or `summary`; the person resolves entries, and `approved` is filled only by `start` with `approve`.
7. **Page.** With no PR in the address, `fromLocation` fetches `/api/local`: a 404 means PR mode and the start page stays, any other answer is local mode. `session` holds the commits, the review data and a map from chunk id to file and chunk; it is `null` in PR mode, which `renderChunk` and `onSelect` check. `explain(url)` streams `/api/local/explain` like `/api/explain/...`, with `base` and `head` set to `local.base` and `local.head` (and `prs` when the address has it). Request changes, Comment, Resolve and Reopen, and the submit button all go through `postReview`, which posts JSON to `/api/review` and redraws the commit list and the review panel from the `review` it gets back; a 400 or 409 puts the server's `error` text next to the control. A change request or comment sends the chunk's `sha`, file, a line hint (first and last new-side line, or `old` plus the old-side lines for a deletion), the diff as text and the body, and its submit button stays off while the body is empty or `sha` is null. There is no per-commit Approve button. A **General comment** textarea sits directly above the submit button; its text is kept in `session.draft`, so a redraw of the panel keeps it, and `renderLocal` starts a new session with it empty. While it holds non-blank text it counts as one open comment, so the label includes it and "Approve all and finish" is not offered. On submit with text, the page posts `change` with `sha` set to `local.head`, and `file`, `lines` and `diff` set to empty strings, and only if that succeeds posts `start`, so the agent sees the entry when it wakes on the new `reviews` item. A failed post shows the error next to the button and starts no round. `review.apply` takes such an entry as it is: the three strings may be empty, `body` may not, and `sha` must still be in the range. An entry whose `file` is empty is a general comment: the entry list shows "General comment" in place of file and lines. On an empty range the panel still has the General comment box and the button when the review file has any entry, resolved or not, because an agent that replied without committing leaves the range empty; with no entry and nothing recorded it has neither. One submit button at the end of the review panel has a label that follows the entries that are open: "Send N comments to agent" posts `start` with `local.head`, and "Approve all and finish" (no entry open) posts it with `approve: true`. The page posts `start` only when the person clicks it, never on load, and the label changes as entries are added, resolved or reopened. After a recorded `start` the page loads `/api/local` and the explain stream again (`reloadLocal`), so it shows what the next run shows: the new range, usually "No unpushed commits", and the open entries, with a confirmation kept in `session.recorded` ("Sent to the agent." or "Approved.", then "The next run shows only new commits."). A selection in a chunk's diff or explanation offers Explain (`askTerm` calls `/api/local/explain-term` with the same `base` and `head` when the address has no PR) and Comment; one in the overview offers only Explain. `#app` stays hidden until the `/api/local` check decides between the start page and the review, so the start page does not flash, and a redraw keeps the commit bodies and the Resolved list the person opened. Everything from the review file or `git log` is set with `textContent`, because the agent writes `reply`.
8. **Summary and plan.** The agent writes a top-level `summary` (`title`, `ticket`, `body` and the optional `plan`) into the review file when it starts a review, so the page and Claude know what the work is for; `skill/diffsplainer-review` describes it. The file comes from another program, so `review.summary` is the only reader: each field is a non-blank string or `null`, a field of any other type becomes `null`, and the whole is `None` when nothing usable is left. A `plan` is a path of up to 1,000 characters, and a summary with only a `plan` is `None`, because the page and the prompt would have no text to show or check. `local.load` returns it as `local.summary` (the browser reads only that, never `review.summary`) and the repository directory name as `local.repo`. `context.local_plan` first reads the file `summary.plan` names: `~` is expanded, a relative path is resolved against the work tree, and the real path must be an existing regular file ending in `.md` that reads as UTF-8 with some text in it, else the lookup goes on (a path outside the repository is allowed, because the agent names it for a plan shared with another repository, and the `.md` check on the real path keeps a symlink from reaching other files). The plan's name on the page is that file's base name. Otherwise it finds the plan in `<git dir>/approach/`: `<branch>.md`, else `<ticket key>.md` when the branch starts with a key (`BH-740`, from `BH-740-slug`, or a number such as `1234`, followed by `-` or the end of the name). A `*.ticket.md` or `*-pr.md` file is not a plan, a detached HEAD has no `approach/` plan (a plan named in the summary still works), and a candidate whose real path is outside `approach/` (a `..` in the name, or a symlink) is refused. The text is clipped to `MAX_PLAN_CHARS`. `claude.local_heading` puts the summary before the commit list, labelled as the agent's claims to check against the diff, not facts, and the plan after it under "Plan (may be older than the code)"; the term prompt gets the summary but no plan. The author under review writes the summary, so when a summary is present `claude.system_prompt` adds a note after `SYSTEM` (outside the data tags, where Claude follows instructions) that tells Claude to prefer the plan or the project instructions for a "why" and to write "The agent says …" when only the summary gives the reason. The overview checks the agent: with a plan or a summary, `claude.overview_schema` adds a required `checks` array (up to 5 strings, each naming the plan item or claim and the file). With a plan it lists plan items the diff does not show, work in the diff the plan does not cover, and summary claims the diff does not support; without a plan, only the summary claims. It is empty when nothing mismatches. The overview sees only an excerpt of the diff (the first 3 chunks of each file, clipped), so the schema tells Claude to write "not seen in the excerpt" instead of "missing" when it cannot be sure. With neither a plan nor a summary, and in PR mode, the schema and prompts are unchanged. The overview event is in the cached stream, so an edit to the summary or plan gets new checks. The `context` event carries only the plan's file name (`plan`, `null` when absent, local mode only), and the page lists it in "Context given to Claude". `_explain_local` adds a SHA-256 prefix of the summary and the plan (`prompt_digest`) to the explanation cache key, so an edit to either gets new explanations. The term cache key includes the hash of the summary but not the plan, because the term prompt has no plan. The page shows the repository name and branch, then an "Agent's summary" label, the title, ticket and body (line breaks kept) in the heading card, and uses the title for `document.title`. When the overview has `checks`, it lists them under "Against the plan" (the `context` event named a plan) or "Against the agent's summary", or shows "No mismatches found." for an empty list. Without a summary the heading is `N unpushed commits on <branch>`.
