# AGENTS.md

Guidance to coding agents working in this repository.

## Project

diffsplainer is a GitHub PR review app. It shows a PR's diff as chunks, with an explanation from a headless Claude Code run next to each chunk. At runtime the backend uses only the Python 3.11+ standard library. The browser UI is plain HTML, CSS and JavaScript in `src/diffsplainer/static/`. pytest is the only dependency, in the `dev` group. Do not add runtime dependencies.

## Commands

- Run the app: `uv run diffsplainer`. The README lists the environment variables.
- Run the tests: `uv run pytest`.
- Check syntax: `uv run python -m compileall -q src`.
- Lint: `uvx ruff check src tests`.

## Tests

Write or change the test first and see it fail before you change the code. Tests live in `tests/` and replace GitHub (`diffsplainer.github` functions) and Claude (`explain_file`, `explain_overview`, `explain_term`) with fakes. Tests of `run_claude` point `CLAUDE_BIN` at `tests/fake_claude.py`, which records its arguments, working directory and environment and answers each schema the app sends (term, chunk batch, overview) with fake text. They never call the network or the real `claude` CLI. Browser checks can run the app with `CLAUDE_BIN=$PWD/tests/fake_claude.py` to avoid real Claude calls.

## Layout

- `diff.py` parses GitHub patches into chunks.
- `github.py` is the GitHub REST client.
- `context.py` gathers project instructions and related PRs.
- `claude.py` builds prompts and runs `claude -p`.
- `server.py` serves the API, the static files and the caches.

## How it works

1. **Diff.** `get_pull_files` requests pages of 100 files until GitHub returns a short page, up to 30 pages, which is GitHub's limit of 3000 files per PR. Each hunk becomes a chunk. A hunk of more than 30 lines is split at runs of unchanged lines, or, for long runs of additions or deletions, at top-level blocks.
2. **Context.** Instruction files come from the base commit: `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md` and `CONTRIBUTING.md` at the root, plus nested `CLAUDE.md` and `AGENTS.md` in directories that contain changed files. `README.md` is a fallback, used only when none of those files was loaded. Related PRs come from the last three commits of each of the first eight changed files. At most 12 commit SHAs are mapped to merged PRs, taken round-robin across the files (first commit of each file, then the second, and so on) so that one busy file cannot use up the cap.
3. **Size cap.** A PR whose additions plus deletions exceed `MAX_CHANGED_LINES` (default 1000) gets one `error` event with `scope: "limit"` and no Claude calls. The diff still loads through `/api/pr`. One batch targets 400 diff lines, but a single chunk longer than that becomes its own batch, so a batch can exceed the estimate. Measured on this repository's PR#1 with the `sonnet` default and a Claude Code login: a batch of 6 chunks (298 diff lines) used 10.6k input tokens and 1.5k output tokens, took 11 s of Claude time and cost $0.057. A batch of 7 chunks (143 diff lines) used 8.6k input tokens and 1.8k output tokens, took 13 s and cost $0.047. Before the isolation flags, an 11-chunk batch in the default Claude Code setup (Opus, with the user's MCP connectors, hooks and `CLAUDE.md` loaded) used 215k input tokens and 3.8k output tokens, took 39 s and cost $1.80, so a PR of 14 calls cost about $25. The overview call is not measured. 1,000 changed lines are about 1,500 diff lines with context, which is 5–8 batches. Extrapolated from the two measured batches, not measured: about $0.25–0.45 and 45–85k input tokens per PR, plus the overview, taking about 15–30 s in total at `CLAUDE_CONCURRENCY=6`.
4. **Explain.** `claude -p` runs with tools disabled and a JSON schema, once per file batch plus once for the overview, in parallel (`CLAUDE_CONCURRENCY`, default 6). Each call passes `--strict-mcp-config`, `--setting-sources ""`, `--disable-slash-commands` and `--no-session-persistence` and sets `ENABLE_CLAUDEAI_MCP_SERVERS=false`, because Claude Code loads the user's MCP servers, hooks and `CLAUDE.md` whatever its working directory. User settings do not load, so `CLAUDE_MODEL` defaults to `sonnet`, and authentication that comes from settings (such as `apiKeyHelper`) does not apply; the Claude Code login does. Every call runs in one private directory per process (`tempfile.mkdtemp`, mode 0700, created on first use and removed at exit), because Claude Code loads `CLAUDE.md` and `.claude/settings.json` from its working directory and `/tmp` is world-writable. One directory for all calls also keeps the working directory in Claude Code's prompt the same between calls. Each explain request also starts a watcher thread that checks the client socket every 0.5 s with `select` and `recv(1, MSG_PEEK)`, which does not consume request bytes. When the client has closed the socket, the watcher sets `gone`. `run_claude` then kills its `claude` process and raises `ClaudeCancelled`, queued batches do not start, no `error` events are sent, and the log is not cached. The PR title, description, project docs, related PRs and file list go inside `<pr_context>`, and diffs go inside `<chunk>` and `<diff_excerpt>`. The system prompt tells Claude that text inside those tags is data from the PR author, not instructions. The tags are not escaped, so content that contains a closing tag can end its block early. The chunk and overview schemas' field descriptions are the prompt for each field: `what` is the effect in one sentence, `why` is the stated reason or "Reason not stated in the PR", and `concern` is a specific, verifiable risk or empty. In the overview, `summary` is the outcome and its stated reason in two sentences at most, `approach` is the main design choice, and `review_focus` lists up to three specific risks. `SYSTEM` sets the writing style (plain language) for every Claude call, chunk batches and overview alike. A selected term is explained by a separate call, `explain_term`: its prompt is `SYSTEM`, the PR title and description (no project instructions or related PRs, so a click takes a few seconds), the chunk when there is one, and the paragraph and the selection in `<paragraph>` and `<selection>` tags. `TERM_SCHEMA` has `meaning` (what the term means in general, one or two sentences) and `here` (what it does in this PR, one sentence).
5. **Stream and caches.** Results stream to the page as Server-Sent Events (`status`, `context`, `overview`, `chunk`, `error`, `done`). When the stream ends, a chunk that has no explanation shows "No explanation returned". A finished stream is kept in `_explain_cache` (LRU, 50 entries) under `owner/repo/number@baseSha..headSha:prs`. A stream is cached only if every call succeeded and every batch got explanations for all of its chunk ids, so an incomplete result is asked for again on the next open. `_pr_cache` holds loaded PRs for 60 seconds (LRU, 50 entries) and drops an expired entry when it sees it. `GET /api/explain-term/<owner>/<repo>/<num>?text=<selection>&around=<paragraph>&chunk=<id>` returns `{"meaning", "here"}` as JSON (`chunk` is absent for the overview). It answers 400 for empty `text`, `text` over 300 characters or `around` over 4,000 characters, 404 for a chunk id that is not in the PR, and 502 with `{"error"}` when Claude fails. It starts the same disconnect watcher, so aborting the request kills the Claude call and nothing is written. `_term_cache` (LRU, 200 entries) holds the answers under a tuple of owner, repo, number, base SHA, head SHA, chunk, selection and paragraph; a failed call is not cached.
6. **Token.** `_token()` in `github.py` resolves the GitHub token once per process: `GITHUB_TOKEN`, then `GH_TOKEN`, then `gh auth token`, else none.
7. **Network.** The server binds to `127.0.0.1`. It has no authentication, and it uses the user's GitHub token and Claude Code login, so it must not be reachable from other machines.
